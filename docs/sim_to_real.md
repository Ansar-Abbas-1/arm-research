# Sim-to-real (M5) — decisions and scaffolding

No hardware is connected during this work; everything here is compile-tested against the existing M0 architecture (`docs/architecture.md`), never run against real motors. See `ROADMAP.md`'s M5 section for the audit this builds on (the 6 risks found in `robot_interface.cpp`, never reviewed before this milestone) and the staged plan these changes are the first step of.

## 1. The commanded/actual position-mismatch check: left as-is, deliberately

`robot_interface.cpp`'s `position_threshold_` (default 10.0 rad, larger than any joint's full range — confirmed inert) was flagged by the M5 audit as a risk. Decided: **not worth fixing right now.** Its only job is catching a divergence between what was commanded and what the hardware reports — a real backstop, but a narrower one than it first appears, and the two mechanisms already planned/scaffolded elsewhere in this milestone (a real velocity clamp on the new interface, and the e-stop interface below) cover the actual dangerous scenarios (a runaway setpoint, an operator-triggered stop) more directly. Revisit only if real-hardware testing turns up a divergence scenario specifically this check would have caught and the others wouldn't.

## 2. `robot_interface_velocity.cpp`: a second, velocity-commanded hardware interface

New node, `src/robot_interface_velocity.cpp`, structurally mirroring `robot_interface.cpp` (same watchdog, torque enable/disable, bulk-read-for-monitoring, service shape) but commanding Dynamixel **Velocity Control Mode** (Operating Mode register = 1) instead of Position Control Mode. Deliberate duplication rather than a shared base class — the two differ in safety-critical specifics, not just which register they write, and forcing a shared abstraction would obscure that rather than simplify it.

**Explicitly scoped down, per instruction**: nothing upstream (`arm_kinematics`/`arm_trajectory`) emits velocity commands yet, and adapting them is out of scope here. This node has no real caller today — it exists so the hardware-facing plumbing is ready when that adaptation happens, not because it's part of the day-to-day pipeline now.

**The key safety difference from position mode, and why it drove the implementation**: a Dynamixel in Velocity Control Mode keeps executing its last-written goal velocity *continuously* until a new command arrives or torque is disabled — unlike position mode, where the motor simply stops making further progress once it reaches its last goal. "Stop writing new commands" is therefore **not** a safe response to a stale command here. The watchdog explicitly bulk-writes a zero velocity to every joint before disabling torque, both on command timeout and on read-failure fault — see `readAndPublish()`'s own comment.

**Command interface**: reuses `/joint_states_out` (`sensor_msgs/JointState`), populated in the `.velocity` field instead of `.position` — the same topic/type `robot_interface.cpp` already subscribes to, so swapping which node is running is the only thing that changes which domain a caller must populate. Avoids a second topic for what is, from upstream's perspective, still "the hardware command channel."

**Safety clamp**: every outgoing velocity is clamped to `~max_velocity_rad_s` (per-joint, YAML array, default `0.1 rad/s` for all six — deliberately slow, matching the ROADMAP's own "reduced speed on first real-hardware run of any new motion" rule) regardless of what upstream commands. Since nothing upstream exists yet, this is the only velocity limit in effect.

**Operating Mode sequencing**: Dynamixel's Operating Mode register can only be changed while torque is disabled, so `setVelocityControlMode()` runs before the first `enableTorque()` call in the constructor — getting this ordering wrong would either silently fail or (depending on firmware) write ignored.

**Protocol constants used** (Protocol 2.0, X/MX-series control table, all overridable via `~` params): Operating Mode address 11, Goal Velocity address 104 (4 bytes), velocity resolution 0.229 rev/min per LSB. Not independently re-verified against real hardware — standard values for this motor family, flagged for confirmation before first live use.

## 3. E-stop: interface only, not implemented

Per explicit instruction: "prepare the basics... do not implement it yet." Both `robot_interface.cpp` and `robot_interface_velocity.cpp` now advertise `/arm_interface/estop` (`std_srvs/Trigger`, matching the existing `/arm_interface/set_torque`/`/arm_interface/reenable_failed_motors` convention rather than a new custom `.srv`). The handler logs an error and returns `success=false` with an explanatory message — **no motor action is taken**. An honest failure, not a silent no-op or a surprise fallback to some other action (e.g. `disableTorque()`) nobody asked for.

**Intended final behavior, documented for whoever implements it**: lock all motors *in place*, not just cut power. `disableTorque()` alone would let the arm droop under gravity — the opposite of "locked." The two mechanisms this milestone already built are each a partial ingredient but not the answer on their own:
- Position mode: the motor already holds its last commanded position under torque: a real e-stop here is closer to "stop accepting new commands, keep holding the current one" — needs confirming the firmware's own internal position-hold behavior is strong enough under disturbance to call that "locked."
- Velocity mode: zeroing velocity (already implemented, see `zeroAllVelocities()`) regulates to zero *speed*, not a held *position* — under a sustained external force the arm can still drift. A real lock here most likely means switching back to Position Control Mode, commanding the current present-position as goal, and holding — not built here.

## 4. Joint-limit sources (URDF vs. YAML encoder ticks): confirmed coherent

Flagged by the audit as two unsynced sources of truth with measured drift (joints 1–3 ≤0.02 rad, joint_4 ~0.017 rad, joint_5 ~0.046 rad). Confirmed: these are coherent for centering (zero offset / `bias`) and scaling (resolution / `sign`) — the measured drift is within expected/acceptable tolerance, not a real divergence. No change made.

## 5. The gripper (joint_6): prismatic joint, rotational actuator — a real conversion, not a unit swap

The earlier M4 gripper redesign made `joint_6` prismatic in the URDF (correct — the fingers genuinely translate) but left `robot_interface.cpp`'s hardware-facing code treating it exactly like every other joint: motor ticks → radians, uniformly. That's the real bug the M5 audit found — not that the joint *should* be rotational, but that the **conversion between the motor's real rotational actuation and the joint's real linear motion was missing entirely.**

Fix: `include/arm_interface/gripper_conversion.h`, a small `GripperConversion` type mapping between the motor's real rotational range (derived from `config/ArmInterface.yaml`'s own `bias`/`sign`/`encoder_min`/`encoder_max` at the gripper's index, not re-hardcoded) and the URDF's linear range (`gripper_linear_min`/`gripper_linear_max`, matching `urdf/arm.urdf`'s `joint_6` `<limit>`). Both `robot_interface.cpp` and `robot_interface_velocity.cpp` convert at exactly the ROS-interface boundary — incoming commands and outgoing state publishes — keeping every *internal* representation (`positions_rad_`/`joint_cmds_` in the position node, `joint_cmds_vel_` in the velocity node) uniformly in the motor's own rotational domain, so the mismatch check and the generic per-joint tick-conversion loop need no gripper-specific branching at all.

**Still an uncalibrated placeholder**, explicitly flagged in the header and the YAML: the conversion assumes a simple affine (linear-in-angle) relationship, exact for an ideal lead-screw/rack-and-pinion, approximate for many real small-gripper mechanisms — this repo has no measurement or spec of the actual mechanism. `gripper_linear_max` (0.025m) is carried over unchanged from the M4 redesign's own "realistic finger travel" estimate; `gripper_linear_min`/`max` and the rotational bounds are now at least *consistently* related rather than being two independently-wrong numbers in two different unit systems.

**Live finding (2026-10-01, Stage 1 read-only session, first real hardware ever connected to this code):** the real gripper's open/close sense came out opposite `arm_sim_validator_node`'s for the same physical motion — exactly the kind of thing the affine placeholder couldn't have gotten right by construction, since nothing in this repo ever recorded which physical rotation direction opens vs. closes the real mechanism. Fixed with an explicit `GripperConversion::invert` flag (`~gripper_invert`, now `true` in `config/ArmInterface.yaml`) rather than guessing which raw number to flip — a one-bit fact about the mechanism's wiring, not a recalibration of the linear range itself. Found and fixed without any motor command: this sign only affects the *read*/publish direction, so it was caught and confirmed purely by watching rviz during the already-running debug-mode (torque-never-enabled) session. **Confirmed matching after the fix**, same session, same method: hand-moved the real gripper, rviz's reported open/close sense now agrees with `arm_sim_validator_node`'s.

**Stage 1 complete** (2026-10-01): read-only verification passed -- real joint positions read correctly, rviz pose matched the physical arm, the one bug found (gripper sign) is fixed and confirmed. Next: Stage 2, first live motion -- not started, needs its own explicit plan (control path, which joint, how the move is issued) before any command is written to a motor.

## 6. Calibration procedures (proposed, not required)

Current state: no calibration step is wired into any launch file. `find_limits.cpp` (manual min/max tracking while a human moves the arm, printed on SIGINT) exists but is a standalone utility, never integrated. Per instruction, this isn't expected to be necessary — these are ideas to have on hand if real-hardware testing ever surfaces a need, not a commitment to build any of them:

- **Zero-offset check**: a small script/service that, given the arm manually posed at a known reference configuration (e.g. hanging straight down, or a jig), reads present-position and reports the `bias` each motor's YAML entry *should* have — a single comparison against the current YAML, not a new calibration procedure, catching drift without requiring the full `find_limits.cpp` range-sweep workflow.
- **Startup consistency check**: at `robot_interface`/`robot_interface_velocity` launch, compare the YAML-derived limits against the URDF's own `<limit>` tags (read via `robot_description`, the way `arm_sim_validator_node` already does) and warn loudly if they diverge beyond a small tolerance — turns "two unsynced sources" into "two sources that are checked against each other," without picking one as authoritative or requiring a new calibration workflow.
- **Gripper mechanism measurement**: the one genuinely open calibration item — measuring the real lead-screw/linkage ratio (or whatever the actual mechanism turns out to be) to replace `gripper_conversion.h`'s affine placeholder with the real relationship, once the gripper is physically accessible.

## 7. Stage 2 prep: torque-enable no longer races a stale goal register

Found while preparing Stage 2 (first real motion, position mode): `robot_interface.cpp`'s constructor calls `enableTorque()` unconditionally at startup, before any `/joint_states_out` command is ever received. A Dynamixel in Position Control Mode actively drives toward whatever is already in its **Goal Position register** the instant torque enables — and that register can hold an arbitrary stale value (a previous session, a power-on default), completely independent of this node's own commanded state. Simply launching `robot_interface` without `debug:=true` could therefore move the arm on its own, before any script or operator command ever runs.

Not caught earlier because every session so far (including all of M5's own Stage 1 work) ran in `debug:=true` mode, where `enableTorque()` is a no-op — this gap only exists on the real, torque-enabled path, which Stage 2 is the first thing to actually exercise.

**Fix**: `seedGoalPositionToCurrentPosition()`, called right before `enableTorque()` in the constructor. Reads present position once (bulk-read setup moved earlier in the constructor to make this possible) and writes it straight back as Goal Position for every joint, so by the time torque enables, "hold current position" is guaranteed rather than assumed. Fails loud (throws, same as the existing port-open checks) if the read or seed-write doesn't succeed, rather than proceeding to enable torque against an unverified register state.

Same class of gap existed in `robot_interface_velocity.cpp` for **Goal Velocity** (a stale nonzero velocity becoming live the instant torque enables) — fixed by calling the already-existing `zeroAllVelocities()` (previously only used on timeout/shutdown) before `enableTorque()` in that node's constructor too.

## 8. Stage 2 single-joint test script

`scripts/stage2_single_joint_test.py` (`rosrun arm_interface stage2_single_joint_test.py --joint N --delta X`): reads one live `/joint_states_in` message, commands joint `N` to its current value plus `X`, holds every other joint at its own current value (see this file's own module docstring for why that's not optional — `robot_interface.cpp`'s commanded-position array otherwise starts at all-zero radians, not "current position"), publishes for `--publish-seconds` (default 1.0), then stops — `robot_interface`'s own `command_timeout` watchdog (default 0.5s) disables torque shortly after the last publish, so the script doesn't need its own stop/hold logic. Per-joint hardware limits (`encoder_min`/`encoder_max`) are still enforced by `robot_interface.cpp` on every write regardless of what this script sends.

## 9. Stage 2, first real motion (2026-10-01): passed

Position mode, non-debug launch, `stage2_single_joint_test.py --joint 6 --delta 0.01`. Log order was as designed: `Goal position seeded…` → `Torque enabled` → command received → writes → command-timeout watchdog (0.5s) → `Torque disabled`. Observed: gripper opened slightly, no other joint moved. Confirms end to end on real hardware: the goal-seeding fix, the hold-others-at-current command pattern, the gripper `LinearToRotational` write path with `gripper_invert`, and the watchdog's disable-torque behavior.

**Caveat before testing any arm joint**: the watchdog's response to a stale command is `disableTorque()`, which drops holding force. That is harmless for the gripper but not for gravity-loaded arm joints (joints 2-4 especially): the arm will sag when the watchdog fires after a test move. Arm-joint tests need either support under the arm or a deliberate hold strategy, not just "stop publishing."

## 10. Re-enable path now re-seeds goals too (2026-10-01)

Gap in §7's fix, found right after it: seeding only ran at node startup. The watchdog (and `set_torque false`) leave the goal registers holding the *last commanded targets*, so the next command's torque re-enable could jump the arm toward them if it had moved or sagged while torque was off. The first joint_5 test ran through this path without incident, but only because nothing had moved in between.

**Fix** (`robot_interface.cpp`): torque re-enable is no longer done on ROS callback threads. `jointStatesOutCb` and `/arm_interface/set_torque true` post a request (`enable_request_`, atomic); the control loop services it on the next tick whose bulk read succeeded, writes that fresh read back as Goal Position, *then* enables torque, and only then sets `start_writing_`. This keeps all `bulkRead_` buffer access on one thread. If the seed write fails, torque is not enabled and the failure is logged. `set_torque true` waits up to 1 s for the loop and reports the real outcome. `reenable_failed_motors` now seeds the rebooted motor's goal from its own present position before enabling (a reboot resets RAM registers, so its goal is not where it was holding). `robot_interface_velocity.cpp`'s `set_torque true` now zeroes goal velocity first.

**Status**: verified live (2026-10-01): joint_5 `--delta -0.05`/`-0.05` run twice back to back without restarting; each run logged `Goal position re-seeded…` before `Torque enabled`, both moved correctly, nothing lurched at re-enable, watchdog disabled torque afterward. (An earlier attempt ran the old binary because the node was relaunched before the rebuild finished; the missing `re-seeded` log line is what exposed it, so check for that line after any rebuild.) **Known, left alone**: `robot_interface_velocity.cpp`'s command callback sets `start_writing_` without re-enabling torque after a watchdog disable (fails safe, nothing moves until `set_torque true`); that node has no caller yet.

## 13. Stage 3 Cartesian tooling: `scripts/stage3_cartesian_reach.py` (2026-10-02)

First Cartesian reach on hardware: target = the live end-effector pose (from the read-only `fk_node`, `rosrun arm_kinematics fk_node`) plus a small `--offset` (default 3 cm up, refused above 10 cm) with the same orientation. It requests a Cartesian-path trajectory (position+pitch IK, base-box collision checks in the generator), prints the plan, refuses on generation failure / any joint over `--max-delta` (0.4 rad) / path deviation over `--max-deviation` (5 mm) / end joints outside the URDF limits, and sends nothing without a typed `yes`. Afterwards it prints the EE error at the end of the move and 0.3 s later.

## 15. Software e-stop: "lock in place" (2026-10-02, position-mode robot_interface)

Replaces the honest-failure stub. **Behaviour**: a latched hold, not a torque cut. Triggering it (service `/arm_interface/estop`, which waits up to 1 s for confirmation, or the fire-and-forget topic `/arm_interface/estop_trigger` `std_msgs/Empty`) latches `EStopLatch` (`include/arm_interface/estop.h`, pure, 7 unit tests). From that instant `/joint_states_out` commands are ignored, `set_torque` is refused in both directions (disabling would drop the lock), enable requests are refused, and the watchdog and write section are inert. On its next tick with a successful bulk read the control loop writes the **fresh present position back as Goal Position and enables torque** (`seedFromLatestReadAndEnableTorque`), so the arm halts and holds where it is, including when it had been sagging with torque off. A hold that cannot be confirmed (no good read, write error) is retried every tick, and the service replies `success=false` rather than claiming a lock it does not have. State is published on the latched topic `/arm_interface/estop_state` (`std_msgs/Bool`). `/arm_interface/estop_reset` clears the latch and moves nothing: the arm keeps holding with torque on (the watchdog is only armed while writing) until the next command or an explicit `set_torque false`.

**Known limits**: (1) a bus communication fault (`max_read_failures_` consecutive read failures) and node shutdown still call `disableTorque()`, which overrides the lock, by design (a dead bus cannot be verified). (2) Not a hardware e-stop: it depends on the node, the USB link and the motors' firmware holding the goal; the breaker on the regulator board remains the only independent stop. (3) The trajectory executor does not know about it: it keeps publishing, `robot_interface` ignores it, and the reach reports a large final error. (4) `robot_interface_velocity` still has the stub (a real lock there means switching back to Position Control Mode, not built). (5) **Control-loop behaviour is compile-tested and the latch logic unit-tested only; it needs hardware verification** (procedure below).

**Hardware test procedure** (operator runs; arm supported): (a) at rest with the stack up, `rosservice call /arm_interface/estop` -> success true, `rostopic echo -n1 /arm_interface/estop_state` true, `rosservice call /arm_interface/set_torque "data: false"` refused, a `reach_pose_cli.py` command ignored (warning in the node log), then `rosservice call /arm_interface/estop_reset`. (b) during a slow reach, `rostopic pub -1 /arm_interface/estop_trigger std_msgs/Empty`: the arm must stop and stay put with torque on. (c) after the watchdog has dropped torque and the arm has sagged, trigger it: the arm must lock where it is, not snap anywhere.

**E-stop hardware check (a), at rest (2026-10-02): passed.** Trigger -> hold confirmed 107 ms later (goal re-seeded from a fresh read, torque on), commands ignored while latched (node log warnings), reset released cleanly and the next command went through the normal re-seed/enable path. Checks (b) trigger mid-motion and (c) trigger after a sag-then-lock are still to do (the service trigger in this session did happen after the watchdog had dropped torque for ~80 s, and the hold applied, but the physical result of that was not reported).

**Known issue, reported by the operator, NOT fixed: re-enabling torque makes the commands jump.** Likely contributors, none verified: (1) `enableTorque()` takes ~100 ms (six sequential writes) during which the trajectory executor keeps advancing, so the first goal written once torque is on is ~0.1 s of trajectory ahead of the arm's present position; (2) position mode has no velocity limit (audit finding 2: no Profile Velocity configured), so any step in the goal is executed at the motor's full speed and looks like a jump however small; (3) a goal step between the held/sagged present position and the first trajectory point. Candidate fixes to evaluate later: set a Profile Velocity register for position mode, ramp the goal from the seeded present position to the commanded one after enable, and/or have the first write after an enable start from the seeded value and slew toward the command.

**E-stop check (b), mid-motion trigger (2026-10-02): PASS** (`scripts/estop_midmotion_test.py`, pose A reach, trigger published 2.50 s in, `velocity_scale` 0.1). Joint speed in the 0.5 s before the trigger: 0.176 rad/s. After the trigger: max joint travel 0.0031 rad at +0.1 s and 0.0046 rad at +0.3 s (about 0.26 degrees, then constant), speed 0.000 rad/s from +0.3 s, drift between +0.5 s and +3.0 s only 0.0015 rad, `/arm_interface/estop_state` true. The interrupted reach was correctly reported as failed (final position error 0.124 m). So: the arm stops within ~0.1-0.3 s of the trigger, travels under 5 mrad after it, and holds without creep. Measured at the slow commissioning speed (0.1 scale); stopping distance will grow with speed. Check (c) (lock after a sag) is still without a physical observation from the operator.

## 16. Hold instead of drop, slew-limited goals, e-stop visible to every sender (2026-10-02)

Two operator problems, one restructure. (1) The command-timeout watchdog dropped torque ~0.5 s after every trajectory (the arm sagged to the singular rest pose), and re-enabling torque made the commanded motion jump. (2) The e-stop existed only inside `robot_interface`; senders did not know about it. This section **supersedes** the watchdog descriptions in sections 3, 7, 10 and 12-14 (kept as history): torque is no longer dropped by a timeout.

**Drive state machine** (`include/arm_interface/drive_state.h`, pure, 13 unit tests with the slew limiter): `TORQUE_OFF / HOLDING / TRACKING / ESTOPPED`. `command timeout` = TRACKING -> HOLDING with **no torque action**: position-mode motors keep driving to their last goal, so the arm stays where the last command put it, whether the trajectory finished or the sender died. Torque changes only on an explicit `set_torque`, an e-stop, or a bus fault (and enabling from OFF re-seeds the goal from a fresh read first). Startup is HOLDING. Operator decision: hold indefinitely (no idle release; `command_timeout` now only defines when a stream counts as ended). Known cost: motors holding a load for a long time heat up; the firmware shuts a motor down on overheat and `robot_interface` already reports hardware errors. Latched topic `/arm_interface/drive_state` (std_msgs/String) shows the state. `set_torque` is executed by the control loop and replies with the real outcome (disable now also waits up to 3 s).

**Jump fix, systematically** (`goal_slew.h`): the goal written to each motor is the commanded one moved toward by at most `max_goal_slew_rad_s * dt` (default 0.5 rad/s per joint, `config/ArmInterface.yaml`) from the goal LAST WRITTEN, never the raw command. A hold no longer needs a torque toggle (removing the ~100 ms enable window), and every remaining discontinuity (resuming from a hold with a sagged arm, enabling from off, a trajectory whose first sample is off the held goal) becomes a ramp. It doubles as a hard speed cap on whatever a sender commands (closes audit finding 2 for position mode): at `velocity_scale` 0.1 (0.2 rad/s) it never clips normal tracking; at higher scales raise it with `velocity_scale`. Joints no command names (the executor never names joint_6) keep the goal already written for them. Log line `Goal slew limiting active` means the arm is catching up.

**E-stop known to every sender**: all three backends publish the latched `/arm_interface/estop_state` (hardware position: real; simulator `arm_sim_validator_node`: now a real e-stop with the same services/topic, so the stack behaves identically in sim; hardware velocity node: publishes "released", its e-stop is still the stub). `trajectory_executor_node` is the single choke point for trajectories: it refuses a new goal while the e-stop is engaged **or the state is unknown** (fail-closed, operator decision; `~require_estop_state:=false` opts out for a backend with no topic), and aborts a running trajectory the moment it engages (`ABORTED: e-stop engaged mid-trajectory`). `reach_target_pose_node` refuses early with a clear message and stops its correction loop. `stage2_single_joint_test.py`, which publishes straight to `/joint_states_out`, checks the state itself; `robot_interface` still ignores commands while latched, as the last line of defence. A bus fault while latched turns torque off but re-arms the hold, so it re-applies when the bus returns.

**Verified offline** (simulator on an isolated master): normal reach OK; e-stop mid-trajectory -> executor aborts, simulated arm frozen (0.0000 rad/s); new reach while engaged refused up front; reach after reset OK; executor with no backend refuses ("e-stop state unknown"), and runs with `require_estop_state:=false`. **Not verified (needs the real arm)**: the `robot_interface` control-loop glue (hold after a trajectory, slew behaviour, resume from hold, set_torque, e-stop in the new state machine, bus fault).

**Known limits**: an explicit `set_torque false` is overridden by the next command (command in TORQUE_OFF = seed and enable), so release only when no sender is streaming. The velocity-mode node still drops torque on its own timeout (it zeroes velocity first) and has the e-stop stub. **Holding indefinitely loads the motors**: on 2026-10-05 motor 4 lost power (overload after prolonged high-torque holding; the operator cut main power) 5 s after a reach ended, in HOLDING. Mitigation so far is the link_4-vertical null-space bias (lower gravity torque on motor 4); not done: reading Present Load and the Hardware Error Status register in the control loop to warn, or relax to a lower holding effort, before the overload protection trips. `position_threshold_` mismatch check unchanged (inert).

## 17. Motor health monitoring (2026-10-05)

**Why.** On 2026-10-05 motor 4 (MX-28) latched an overload error and motor 3 (MX-106) an overheating error. Both are in the Shutdown mask (0x34), so the firmware cut their torque itself while still answering position reads; `robot_interface` reported HOLDING with torque "on" and the reaches ended 0.3 to 0.7 m off. Cause of the blindness: `GroupBulkRead::addParam` accepts ONE address range per motor ID and returns false for a second, so the hardware-error register (70) that was added next to the position (132) was never read, and the decoding code behind it never ran (it also mislabelled bits 2 and 4). `motor_diag` (read-only, stack stopped) is the offline tool that found it.

**What runs now** (`monitorMotorHealth`, control-loop thread, policy in `motor_health.h`, unit tested):
- The status packet's ERR byte of every position read is checked for the Hardware Alert bit (0x80): a free detector every cycle (about 16 ms).
- Load, voltage and temperature ride along with every position read: the per-motor bulk-read range was widened from the 4-byte position to registers 126..146 (21 bytes), so there is NO extra bus transaction. Each separate transaction costs a full USB latency period (16 ms with the default FTDI latency timer, which is why `/joint_states_in` runs at about 62 Hz and not the 100 Hz the loop asks for), so a second read per cycle would have roughly doubled the cycle time; the first version of this feature did exactly that (a 77-byte block at 2 Hz, whose wire time I wrongly quoted as the cost). Now the added cost is about 17 bytes x 6 motors x 10 us, roughly 1 ms per cycle.
- Hardware Error Status (address 70, not contiguous with that block) is read in its own tiny group, only when the alert bit is seen, at startup, and every `error_poll_period_s` (2 s) as a safety net. Each motor's own Temperature Limit (address 31) is read once at startup.
- Levels: FAULT = latched hardware error (or alert with no readable detail); WARN = temperature within `temp_warn_margin_c` (3 C) of the motor's own limit, load at or above `load_warn_fraction` (80 %) for `load_sustain_s` (5 s), or input voltage outside 10 to 14.5 V. All thresholds are heuristic starting values.
- Outputs (published at `status_rate_hz`, 2 Hz): `/arm_interface/motor_status` (`diagnostic_msgs/DiagnosticArray`, one status per joint with temperature, limit, load %, voltage, error), `/arm_interface/motor_load` (`sensor_msgs/JointState`, `effort` = signed load in % of max torque; sign follows the motor, not the joint convention). Both are meant for logging: record them with `rosbag` while holding poses to calibrate the URDF masses.
- Escalation (`estop_on_hardware_error`, default true): any FAULT engages the software e-stop (senders fail closed, the other joints hold) and the motor is excluded from torque writes (`enableTorque` skips it; a failed write there would end the process). `estop_reset` is REFUSED while a motor still has a latched error; reboot or power-cycle that motor first, then reset. Warnings never escalate.
- Recovery (added after the first power cycle, 2026-10-05): a motor that leaves FAULT (rebooted or power-cycled) is NOT holding, because the e-stop hold and the last torque-enable skipped it while it was faulted. If torque is supposed to be on, the control loop seeds that motor's goal to its own present position and enables its torque (`seedAndEnableMotor`, one motor, volatile goal register). When reads resume after a bus failure the error register is polled at once, since the cached flag was stale for up to 2 s after the power cycle and the hold skipped joint 4 in that window. `/arm_interface/reenable_failed_motors` (reboot, seed, enable) now works: it keys off `motor_errors_`, which the dead hardware-error read never filled, so it always answered "No motors were in a failed state"; it shares `seedAndEnableMotor` and is the way to clear a latched error without power-cycling the whole arm.
- Observed on hardware (power cycle with the stack running): voltage warnings at 8.3 to 7.3 V, five failed reads, bus fault, torque disabled (ESTOPPED to TORQUE_OFF), the e-stop latch survived, motors came back healthy, the hold re-applied by itself. The latch-and-hold behaviour through a power loss is as designed.
- Startup: before torque is enabled the same check runs, so a motor with an error latched from the previous session is reported at once, the e-stop is raised and torque is not enabled on it.

**Status: compile-tested and the pure logic unit-tested only; the bus glue has not run on hardware.** Check that `/joint_states_in` still runs at its previous rate (about 62 Hz); the alert-triggered and 2 s error reads each cost one USB round trip. Raising the loop rate itself is a host setting, not done here: set the FTDI latency timer to 1 ms (`echo 1 | sudo tee /sys/bus/usb-serial/devices/ttyUSB0/latency_timer`), after which the loop should approach the requested 100 Hz.

**Hardware test plan** (operator runs). (a) With motors 3 and 4 still latched from 2026-10-05 and the arm supported or lowered (the healthy joints will hold while joints 3 and 4 are limp, so it can fold): start the stack and expect ERROR lines naming ID 3 (overheating) and ID 4 (overload), `Software e-stop engaged`, `drive_state` ESTOPPED, no torque on those two, and `estop_reset` refused with the reason. (b) After rebooting the motors: clean start, `motor_status` all OK, `motor_load` publishing; hold pose A and record the loads. (c) Do not try to provoke an overload on purpose.

**Known limits.** `robot_interface_velocity` has the same dead hardware-error read and no monitoring. WARN only logs and publishes: nothing yet stops new moves when a motor is near its temperature limit (the firmware will cut torque at the limit, and the arm falls). The load scale assumes MX-series units (0.1 % per count); X-series reports current in mA at the same address (`load_full_scale_raw`).
