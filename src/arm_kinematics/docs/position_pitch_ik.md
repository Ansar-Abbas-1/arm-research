# Position + pitch IK — derivation

Builds on [`inverse_kinematics.md`](inverse_kinematics.md) (why a generic full 6D pose target is unreachable on this chain, and the rank-4 structure of its Jacobian) and [`resolved_rate.md`](resolved_rate.md) (the damped right-pseudo-inverse + null-space math this solver reuses).

## Why this exists

`InverseKinematicsSolver` targets a full 6D pose with 5 joints. The Jacobian of this chain has **rank 4 at every configuration**, not 5 (σ₅ ≈ 1e-16…1e-19 at random in-limit configurations; derivation in [`kinematics_report.md`](kinematics_report.md) §2.2): the common horizontal axis of joints 2–5 forces the end-effector twist to satisfy `ω_r = 0` and `v_θ = r·ω_z`. Consequences:

- The reachable poses are a **4-dimensional** submanifold of SE(3): roll is identically 0 and yaw is slaved to the position azimuth (`atan2(p_y,p_x)`, or +π when the tip is behind the base axis). They are *dependent* variables, not free ones.
- The null space of `J` (and of the 4×5 task Jacobian below) is **1-dimensional** for the full-pose task as well. A secondary objective (e.g. "keep `link_4` vertical") has room to live in even then — but only for targets that are on the reachable manifold; a generic 6D target is off it, so the full-pose solve ends at a nonzero best-fit residual and the null space is not exploitable in a meaningful way.

Why a position + pitch task is still the right one: the tool's pitch is the one independent orientation quantity (rotation about the end-effector's own local Y axis, the same convention `ComputeResolvedRateVelocity` uses for velocity control; the tool Y axis equals `â` for every `q`, so the pitch row of the task Jacobian is the constant `[0,1,1,1,1]`). Asking for position + pitch asks for exactly the 4 independent degrees of freedom the arm has, and nothing that is already implied (roll, yaw) or unreachable. `PositionPitchIkSolver` is therefore equivalent to the full-pose solve *restricted to the reachable manifold*, with the 1-D null space (the planar self-motion) made available to a secondary posture task on every `Solve()`, automatically — not something that has to be separately streamed or gated behind a live control loop.

## Task and iteration

At each Newton iteration, evaluated at the current iterate `q_k`:
```
pose_k = FK(q_k)
e_pos = p_target − p_k                                    ∈ ℝ³
ê_pitch = R_k · [0,1,0]ᵀ                                   (current iterate's own local Y axis)
e_rot = RotationVector(R_target · R_kᵀ)                    ∈ ℝ³  (full angle-axis pose error)
e_pitch = ê_pitch · e_rot                                  ∈ ℝ   (component of the rotation error along pitch)
e_task = [e_pos ; e_pitch] ∈ ℝ⁴
J_task = [ J_v ; ê_pitchᵀ J_ω ] ∈ ℝ^{4×5}                  (identical construction to resolved_rate.md)
```
`e_pitch`/`J_task` use the **current** iterate's own local Y axis at every step, not a fixed reference — the same body-frame convention `ComputeResolvedRateVelocity` uses, kept consistent between the velocity-level and position-level solvers rather than inventing a second definition of "pitch."

Each step is a single damped right-pseudo-inverse solve (`task_space_math.h`, shared with `ComputeResolvedRateVelocity`) — Chiaverini variable damping, so a well-conditioned iterate takes the exact undamped Gauss-Newton step, tapering only near an actual singularity:
```
Δq = J_taskᵀ (J_task J_taskᵀ + λ²(σ_min) I)⁻¹ e_task
```
clamped to `max_step` (inf-norm) as a safety margin, same convention as `InverseKinematicsSolver`.

**While the primary task hasn't yet converged**, the step is also subject to a backtracking line search (`max_inner_retries`): only taken if it actually reduces `‖e_task‖²`, otherwise halved and retried, and the outer loop stops entirely if no improving step is found even after halving that many times. Originally this solver had no such check at all (Chiaverini damping conditions the step *direction* near a singularity, but says nothing about whether the step is a good idea) — that was a real bug, found via `arm_trajectory`'s Cartesian-path tracking: on an interior waypoint this solver couldn't actually reach (expected, off the reachable submanifold — see `arm_trajectory/docs/trajectory_generation.md` Finding 2), it kept taking full `max_step`-clamped steps every iteration regardless of whether they helped, for the whole `max_iterations` budget, wandering 2–3.5 rad away from a good warm-started seed. `InverseKinematicsSolver` never had this problem, since its own Levenberg-Marquardt scheme never accepts a non-improving step in the first place. **This check is only engaged when no null-space secondary task is configured.** A configured bias mixes secondary-task work into every step from the very first iteration, not just after primary convergence (see `NullspaceBiasImprovesVerticalAlignmentAtConvergence`), and its leakage can transiently raise the primary cost well before real convergence too — a cost-based rejection can't distinguish that from genuine divergence, and rejecting it would starve the secondary task of exactly the iterations the fix in the null-space section below exists to give it. The bug this line search fixes was itself only ever observed with no secondary task active, so gating it that way costs nothing.

**Convergence** is position + pitch only, reported the same `[position(3); rotation(3)]` residual layout as `InverseKinematicsSolver::IkResult` — but only the position and pitch-axis-projected component of that 3-vector rotation residual are actually driven toward zero; the remaining two rotation components are reported for information only (whatever roll/yaw the run happened to land on).

**Restarts** on non-convergence use the same policy as `InverseKinematicsSolver::Solve` (random reseed within joint limits, keep the best/lowest-residual result) — this chain's distinct solution basins are a property of the chain, not of which task dimension is being solved for.

## Null-space secondary task, applied at every step

If `nullspace_secondary_link_solver`/`nullspace_gain` are configured (construction-time, not per-call — see the header for why), the same `qdot0` bias `ComputeResolvedRateVelocity` computes (Liegeois gradient toward vertical, see `resolved_rate.md`) is recomputed fresh each iteration (the secondary link's pose changes as `q` does) and projected into `J_task`'s null space, added to the primary Newton step. This has a genuine fixed point at exact vertical alignment: writing the bias as `q̇₀,ᵢ = k · ẑ_world · (zᵢ × â)`, at `â = ẑ_world` the scalar triple product `ẑ_world · (zᵢ × ẑ_world) = zᵢ · (ẑ_world × ẑ_world) = 0` for every `i` (cyclic identity on the scalar triple product) — so the bias vanishes exactly there, not just approximately. Driving it iteratively to convergence (rather than applying it for one control tick) is therefore well-posed: the solver doesn't just nudge toward vertical, it actually settles there, subject to whatever the position+pitch constraint still allows.

`nullspace_gain` here plays the role of a per-iteration **step** gain (radians added directly, every Newton step), not a rad/s **rate** the way it does in `ComputeResolvedRateVelocity` (where the caller multiplies by `dt`, ~0.02s at 50Hz, before it becomes an actual position change) — the two contexts need separately-tuned values, confirmed the hard way: `nullspace_gain=0.4` (resolved-rate's own default, the natural value to reach for) made this solver fail to converge at all on an otherwise-easy target, since applied without any `dt` scaling it's a ~50x larger per-step contribution than the same number means in the velocity context. `0.05` converges cleanly on the same target. `PositionPitchIkOptions::nullspace_gain` still defaults to `0.0` (off), same as `ComputeResolvedRateVelocity`'s default — this is a caution for whoever turns it on, not a change to the default policy.

## `converged` reflects the true final state, not a mid-loop latch

Letting the loop keep running past primary convergence (previous section) introduced a second bug, caught live via `rosservice call /solve_position_pitch_ik`: `converged` was set `true` the instant primary (position+pitch) convergence was *first* observed inside the loop, then left untouched while the loop kept iterating for the secondary task. The null-space projection is damped, not exact, so its small per-step leakage into the primary task can — over the many extra iterations the first fix now allows — drift position error back out of tolerance by the time `max_iterations` is exhausted, while `converged` stayed stuck at its earlier `true`. Observed live:
```
converged: True
residual: [-0.00296, 0, 0.00154, 0, -0.00783, 0]   # position error ≈ 0.0033 m
iterations: 200
```
against `position_tolerance: 1e-4` — a clear inconsistency. Fix: `converged` (and `residual`) are now computed exactly once, unconditionally, from a fresh FK evaluation of the loop's *final* `q` after it exits — never latched mid-loop. `converged` now means "the returned `joint_positions` actually satisfy tolerance," which is the only thing a caller should be able to assume from it.

## Two more bugs, found live through `arm_trajectory`'s day-to-day pipeline

Once this solver became the actual IK behind `/reach_target_pose` (arm_trajectory's Finding 5), two more real bugs surfaced from genuine interactive use — neither visible from a standalone `Solve()` call in isolation.

**Bug 3 — no cost check meant wandering, not just leaking.** A Cartesian-path interior sample this solver couldn't actually reach (expected — off the reachable submanifold, see `arm_trajectory/docs/trajectory_generation.md` Finding 2) kept taking full `max_step`-clamped steps every iteration regardless of whether they helped, for the entire `max_iterations` budget, unlike `InverseKinematicsSolver`'s Levenberg-Marquardt accept/reject, which never takes a non-improving step at all. Measured: joint values wandered 2–3.5 rad away from a good warm-started seed over 20 iterations, tripping `arm_trajectory`'s duration-scaling sanity cap outright. Fixed with `max_inner_retries`: a backtracking line search on `‖e_task‖²`, engaged only when no null-space task is configured (a configured bias mixes secondary-task work into every step from the start, and its own leakage — see below — can't be told apart from genuine divergence by a cost check).

**Bug 4 — the restart/selection logic didn't know alignment existed.** With a null-space task configured, a seed can be excellent — already at the target, well-aligned — and *still* report `converged=false`, purely from secondary-task leakage (bug 2's mechanism, but now large: measured **0.0064 m against a 1e-4 m tolerance, a 64x overshoot**, after 200 unconditional secondary-only iterations from an already-exact seed). `Solve()`'s restart loop, seeing `!converged`, would then reseed from a **completely random** joint configuration and keep it purely for having marginally lower position residual — discarding whatever alignment the original near-perfect seed had already achieved, since alignment never entered the comparison at all. Confirmed live: from a real configuration with alignment `-0.78` (dot with world-up; fixed point is `+1`), the restart search returned alignment `-0.81` — *worse*, from an unrelated basin, while the original seed alone (if trusted) was already close to converging well.

Two changes, together: (1) a **drift cap** (`kDriftCapMultiplier = 10`) on secondary-only iterations — once primary has been satisfied even once, a step is only taken if it keeps the primary residual within `10x` tolerance, halving and retrying otherwise, same backtracking mechanism as Bug 3; this bounds the leak at its source instead of letting it run unchecked for the rest of the budget. (2) `Solve()`'s restart/selection now uses that same `10x` bound as "acceptable" instead of strict `converged` when a null-space task is configured, and among acceptable candidates prefers the better-aligned one — so a good, slightly-leaked seed is kept over a random, poorly-aligned "exact" restart. `PositionPitchIkResult::converged`, as returned by `Solve()` (not `SolveFromSeed`) with a null-space task active, now reflects this same acceptable bound rather than strict tolerance — deliberately, since reporting the strict value would call a result this function *chose on purpose* a failure. Re-verified on the exact live case: alignment `-0.78 → -0.47` (real progress toward the `+1` fixed point), `restarts_used=0`, `converged=true` — the seed's own progress kept, not thrown away.

**Honest limitation, unchanged by this fix:** the bias is still a local, gradient-following correction from wherever the seed lands — it improves alignment relative to that seed's own basin, but does not search across qualitatively different configurations (elbow-up vs. elbow-down, wrist-flip) that might reach the same position+pitch with dramatically better alignment. Finding *that* would need an explicit multi-seed search scored on alignment, not just position residual — a different feature, not fixed here.

## Testing

`test_position_pitch_ik.cpp`: a target's position+pitch, reconstructed via FK from a known random reachable configuration, is matched by the converged solution (independent check — the *joint values* need not match the seed configuration, since roll/yaw and the redundant DOF mean multiple configurations can share the same position+pitch); a small random-target convergence benchmark (mirroring `inverse_kinematics.md`'s own, at a smaller N to keep the suite fast); the null-space bias measurably improves the converged configuration's vertical alignment relative to the same target solved without it, in the majority of an 8-target sweep — not every single one, a redundant task's final basin is path-dependent and the no-bias baseline itself has some run-to-run variation (see `max_inner_retries`' own note above), so "always" was never a claim this test should have made (with-vs-without isolation, same methodology as `ResolvedRateNullspaceTest`); `nullspace_gain=0` matches no secondary solver at all; and a target whose orientation is deliberately *not* on this arm's reachable 5D submanifold (an arbitrary roll/yaw baked into the full pose handed to `InverseKinematicsSolver`, which fails to converge on it) still converges here, since only its position+pitch component — which *is* independently reachable — is ever asked for.

## Posture optimisation (2026-10-05): why the old null-space bias did nothing, and the replacement

**Measured problem.** Over 60 random reachable targets with the service settings (gain 0.05, 200 iterations, warm start 0.3 rad off), link_4's mean tilt from vertical was 39.4 deg without the bias and **41.6 deg with it** (28/60 improved by more than 5 deg, 27/60 got worse by more than 1 deg; best achievable on the self-motion manifold 9.6 deg). The poses used for hardware tests (pose A, the pivot) already have link_4 within 0.3 and 3.3 deg of vertical, so the bias had nothing to do there and looked inert.

**Causes.**
1. *Wrong objective.* It ascended the signed `a = up . z_link`. A link vertical but pointing down (a = -1) is a stationary point of `a` and was pushed up through horizontal; the real goal, a vertical LINE (zero gravity moment about the horizontal joint axes, up or down), is `|a|`.
2. *Too slow.* With `grad(a)_i = up . (w_i x z_link)` (w_i = world joint axis), `|grad a|` is proportional to the sine of the tilt, so a fixed-gain step converges linearly at a rate of order gain * sin^2(theta): 289 to 925 iterations in the probe against a 200 cap.
3. *Entangled with the Newton loop.* The bias was added to every damped Newton step, with a drift-cap backtrack that stopped it as soon as the primary task leaked.
4. *Local only.* The 1-D self-motion manifold has discrete branches (elbow up/down). A local method cannot change branch, which accounts for the remaining gap (9 of 60 targets still more than 10 deg above the best found).

**Replacement** (`OptimizePosture` in `position_pitch_ik.cpp`, run after the primary task converges). With `J_t` (4 x n) the task Jacobian, `V_r` the right singular vectors of its non-zero singular values, `s = sign(a)` (s(0) = +1):
`g = s * grad(a)`, `g_N = (I - V_r V_r^T) g`, step `lambda = min(max_step, (1 - |a|) / |g_N|)` along `g_N / |g_N|`, then a Newton retraction onto the manifold (up to 8 damped steps to half the tolerance). A step is accepted only if the primary task stays inside its tolerance and `|a|` strictly increases, else `lambda` is halved. Near vertical, `1 - |a| ~ theta^2 / 2` and `|g_N| ~ c*theta`, so `lambda ~ theta / (2c)` and the tilt halves each iteration. Stops on `|g_N| < nullspace_tolerance`, no accepted step, `nullspace_max_iterations`, or the displacement budget (`nullspace_max_displacement`). `nullspace_gain != 0` now only enables it. Options: `nullspace_max_step` (0.1 rad) and `nullspace_max_iterations` (100), both heuristic.

**Result** (same 60 targets): mean tilt 12.1 deg (was 41.6), improved by more than 5 deg in 54/60, worse by more than 1 deg in 1/60, more than 10 deg above achievable in 9/60. Through `trajectory_service_node` from the rest pose: forward-low target 47.3 -> 0.1 deg, high-near 2.1 -> 0.1 deg, forward-mid 37.7 -> 34.2 deg (joint_4 reaches its 0.0 lower limit).

**Other changes in the same fix.** (a) `SolveFromSeed` now refines up to 6 Newton steps below 10% of the tolerance once inside it. Stopping at the first iterate inside the loose path-tracking tolerance (1e-3 m) made each Cartesian-path sample jump by up to tolerance/|J|, which does not shrink when the duration grows; with the bias off, an 8 cm move at 0.1 rad/s failed the runaway guard before this and plans in 7.2 s after it. (b) `GenerateCartesianTrajectory` solves its goal (reachability and duration seed) without the posture task, since a fully optimised goal can sit far from the start while the path only drifts at `nullspace_max_rate`. (c) The restart selection in `Solve()` and `ComputeResolvedRateVelocity` use the vertical line (`|a|`). `resolved_rate` is velocity-level and unchanged apart from the sign. teleop_node still has its null-space call commented out (commit 840979b); it was not re-enabled.

**Known limits.** No branch switching (it would need a joint-space path check, since the executor interpolates straight in joint space); joint-limit margin is not penalised, so the optimum can sit against a limit (forward-mid above); diagnostic `probe_nullspace` (built with the tests) reproduces the statistics.
